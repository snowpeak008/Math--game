# IdleFramework 输入规则说明（中文）

> 依据源码整理：`src/idleframework/model/{game,nodes,edges}.py`、`dsl/grammar.lark`、`dsl/compiler.py`、`engine/segments.py`、`engine/variables.py`。
> 每一条都标了“引擎是否真的计算”，因为 **schema 能写进去 ≠ 模拟会生效**。

## 1. 整体结构

一个游戏 = 一个 JSON 文件（`GameDefinition`）：

```json
{
  "schema_version": "1.0",
  "name": "我的游戏",
  "nodes": [ ... ],            // 所有“东西”：资源、生产者、升级、转生……
  "edges": [ ... ],            // 节点之间的关系：谁产出到哪个资源、谁消耗谁……
  "stacking_groups": { "upgrades": "multiplicative" }   // 升级叠加组
}
```

- 每个节点都有 `id`（全局唯一）和 `type`（决定字段），可选 `tags`。
- 校验在加载时进行（`GameDefinition._validate_game`）：ID 唯一、边的两端存在、升级 target 存在、叠加组已定义、公式能编译、tickspeed 最多一个。
- 输入方式目前有 4 种：① 手写 JSON 后 `idleframework analyze 文件.json`；② 英文图形编辑器 `/editor`（节点连线）；③ API `POST /api/v1/games/`；④ **新增的中文表格录入页 `/input`**（本次开发，见《界面设计方案.md》）。

## 2. 常见放置概念 → 怎么填

| 你游戏里的概念 | 节点/字段 | 引擎是否计算 |
|---|---|---|
| 金币、钻石、转生币 | `resource`：`initial_value`、`capacity` | ✅ |
| 生产者（矿工/工厂） | `generator`：`base_production`、`cycle_time`、`cost_base`、`cost_growth_rate` + 一条 `production_target` 边 | ✅ |
| 价格成长 1.15 | `cost_growth_rate: 1.15`，第 n 个价格 = `cost_base × 1.15^(n-1)` | ✅ |
| **多货币价格**（金币+钻石） | `cost` 写成列表：`[{"currency":"gold","amount":15000},{"currency":"diamond","amount":10}]`；生产者也可以（每项都按成长率涨价，可单独写 `growth_rate`） | ✅（fix2 新增） |
| **购买门槛**（荣誉值 ≥ 100 才能买，不扣） | `requires: [{"currency":"honor","amount":100}]`，每次购买都重新检查，**不消耗** | ✅（fix2 新增） |
| 专属货币（某件物品专用的券） | 普通 `resource` + 只在那件物品的 `cost` 列表里出现 | ✅ |
| 倍率升级 x2 / +50% | `upgrade`：`upgrade_type`(multiplicative/additive/percentage)、`magnitude`、`cost`、`target`(生产者ID 或 `_all`)、`stacking_group` | ✅ |
| 同类升级怎么叠加 | `stacking_groups` 里每组 `multiplicative`/`additive`/`percentage` | ✅ |
| 转生 | `prestige_layer`：`formula_expr`、`layer_index`、`reset_scope`、`persistence_scope`、`currency_id` | ⚠ 能执行，但**优化器不会自动决定何时转生** |
| 自动购买 | `autobuyer`：`target`、`interval`、`bulk_amount`(1/10/max)、`condition` | ✅ |
| 限时增益/概率触发 | `buff`：`buff_type`(timed/proc)、`multiplier`、`duration`、`proc_chance` | ✅（按期望值） |
| A 的数量加成 B（协同） | `synergy`：`sources`、`formula_expr`、`target`，效果 = 1 + 公式值 | ✅ |
| 持续消耗（维护费） | `drain`：`rate`、`condition` + `consumption` 边指向资源 | ✅ |
| 全局速度 | `tickspeed`：`base_tickspeed`（最多 1 个） | ✅ |
| 暴击期望 | `probability`：`expected_value`、`crit_chance`、`crit_multiplier` | ⚠ 仅贪心标记“期望值近似” |
| 由公式改别的数值 | 边 `state_modifier`：`formula`、`target_property`、`modifier_mode`(set/add/multiply) | ✅ |
| 计算中间量 | `register`：`formula_expr` | ✅ |
| **解锁条件**（达到 X 才出现） | `unlock_gate` / 边 `unlock_dependency` | ❌ **能写不生效** |
| 成就/里程碑（25 个翻倍） | `achievement` | ❌ **能写不生效**（示例 minicap 里的里程碑实际不起作用） |
| 经理人 | `manager` | ❌ |
| 转换器/合成（A→B） | `converter` | ❌ |
| 生产生产者（AD 维度式） | `nested_generator` | ❌ |
| 献祭、多选一天赋、队列、门、结束条件 | `sacrifice`/`choice_group`/`queue`/`gate`/`end_condition` | ❌ |

> 新加的 `POST /api/v1/games/validate` 会对标 ❌ 的节点给出警告：“目前模拟引擎不会生效”。

## 3. 必须知道的隐含规则（容易踩坑）

1. **价格只写一个数字时（旧格式，完全兼容）**：生产者用它“产出的那个资源”来买；升级用它 target 生产者的货币；`_all` 升级用**第一个资源**。要指定货币或多种货币，请把 `cost` 写成列表（见第 7 节）。旧示例（如 minicap 的 `angel_x2_*`）仍按旧规则扣金币。
2. **第一个 resource 是“主货币”**：分析器用它算产量、给初始 50 金币、找购买货币的兜底。
3. 生产者没有 `production_target` 边就不产出任何东西。
4. `cost_growth_rate ≥ 1.30` 会被分析器直接判成“进度墙”（硬编码规则）。
5. 分析最多模拟 500 次购买，之后会**静默停止**（已知问题，中文界面会提示）。
6. 中文游戏名：原服务端会生成空 ID 导致 500 错误，本次已修复为 `game-<哈希>`（`server/game_store.py::_slugify`）。

## 4. 公式 DSL

语法（`grammar.lark`）：`+ - * / % **`、比较 `> >= < <= == !=`、括号、科学计数 `1e15`。
函数：`sqrt cbrt log ln`（log 与 ln 都是自然对数）`log10 abs min max floor ceil clamp(x,lo,hi) round sum prod`（见 `dsl/compiler.py::_SAFE_BUILTINS`）。

可用变量（`engine/variables.py::build_state_variables`，ID 中非字母数字会变成 `_`）：

| 变量 | 含义 |
|---|---|
| `elapsed_time` / `run_time` | 总时间 / 本轮（转生后）时间 |
| `owned_<id>` | 生产者拥有数 |
| `level_<id>` | 等级 |
| `total_production_<id>` | 该节点累计产出 |
| `balance_<资源id>` | 资源当前值 |
| `lifetime_<资源id>` | 资源累计获得 |
| `lifetime_earnings` | 所有资源累计获得之和 |

例：转生收益 `150 * sqrt(lifetime_earnings / 1e15)`；协同 `owned_miner * 0.01`（每个矿工 +1%）。

## 5. 示例：3 生产者 + 升级 + 转生 + 自动购买

```json
{
  "schema_version": "1.0", "name": "Example",
  "stacking_groups": {"upgrades": "multiplicative", "prestige_bonus": "multiplicative"},
  "nodes": [
    {"id": "gold", "type": "resource", "name": "金币"},
    {"id": "soul", "type": "resource", "name": "灵魂"},
    {"id": "miner", "type": "generator", "name": "矿工", "base_production": 1, "cost_base": 10, "cost_growth_rate": 1.15, "cycle_time": 1},
    {"id": "drill", "type": "generator", "name": "钻机", "base_production": 8, "cost_base": 100, "cost_growth_rate": 1.15},
    {"id": "factory", "type": "generator", "name": "工厂", "base_production": 60, "cost_base": 1100, "cost_growth_rate": 1.15},
    {"id": "x2_miner", "type": "upgrade", "name": "矿工x2", "upgrade_type": "multiplicative", "magnitude": 2, "cost": 500, "target": "miner", "stacking_group": "upgrades"},
    {"id": "rebirth", "type": "prestige_layer", "name": "转生", "formula_expr": "floor(sqrt(lifetime_gold / 1e6))", "layer_index": 0,
     "currency_id": "soul", "reset_scope": ["gold", "miner", "drill", "factory", "x2_miner"], "persistence_scope": ["soul"]},
    {"id": "auto_miner", "type": "autobuyer", "name": "自动买矿工", "target": "miner", "interval": 5, "bulk_amount": "max"}
  ],
  "edges": [
    {"id": "e1", "source": "miner", "target": "gold", "edge_type": "production_target"},
    {"id": "e2", "source": "drill", "target": "gold", "edge_type": "production_target"},
    {"id": "e3", "source": "factory", "target": "gold", "edge_type": "production_target"}
  ]
}
```

“灵魂给全体产量加成”需要额外写 `synergy`（`sources:["soul"]`、`formula_expr:"balance_soul * 0.1"`、`target: 每个生产者各一个`），或用 `state_modifier` 边。

## 6. 多个玩法系统怎么放进来

- **多条产出线**（金币线 + 矿石线）：建多个 resource，生产者各自用边指向自己的资源；因规则 3.1，每条线只能用自己的产出买东西。
- **跨系统转换**（矿石→金币）：`converter` 目前不生效，只能用 `state_modifier` / `synergy` 公式近似。
- **解锁顺序**：`unlock_gate` 不生效 → 目前只能靠价格自然把后期内容“推后”。
- **RPG/战斗/抽卡/离线收益**：框架没有对应节点。

结论：**单货币 + 生产者 + 倍率升级 + 自动购买 + 协同** 能较准确录入；**多货币购买、解锁、成就、转换、多玩法循环** 需要扩展引擎后才能真正参与模拟。


## 7. 多货币价格与购买门槛（fix2）

### 7.1 JSON 写法

```json
{"id": "p_shop_all", "type": "upgrade", "upgrade_type": "multiplicative", "magnitude": 2,
 "target": "_all", "stacking_group": "shop",
 "cost": [{"currency": "gold", "amount": 60000}, {"currency": "diamond", "amount": 40}]}

{"id": "h_shop_1", "type": "upgrade", "upgrade_type": "multiplicative", "magnitude": 3,
 "target": "mine", "stacking_group": "shop",
 "cost": 2000, "requires": [{"currency": "honor", "amount": 100}]}

{"id": "diamond_mine", "type": "generator", "base_production": 0.05, "cost_growth_rate": 1.35,
 "cost": [{"currency": "gold", "amount": 400}]}
```

- `cost` 写数字 = 旧格式（货币按第 3 节第 1 条推断）；写列表 = 每一项 `{currency, amount}` 都要付。
- 生产者的列表价格：`amount` 是第 1 个的价格，第 n 个 = `amount × 成长率^(n-1)`；某项可写 `growth_rate` 单独设成长率，否则用生产者的 `cost_growth_rate`。写了列表就不用再填 `cost_base`。
- `requires`：每项 `{currency, amount}` 表示“该货币余额 ≥ amount 才能买”，**不扣**，每次购买都会重新检查。
- 保存后读回的 JSON 里，列表价格出现在 `costs` 字段（`cost`/`cost_base` 保留第一项数值给旧代码用），两种写法都能再次导入。

### 7.2 表格界面（/input）怎么填

| 列 | 写法 | 例子 |
|---|---|---|
| 价格 / 基础价格 | 数字，或 `货币ID:数量; 货币ID:数量`（分隔可用 `;` `；` `+`，冒号可用 `:` `：` `=`） | `gold:15000; diamond:10` |
| 购买门槛 | `货币ID>=数量; …`（也可写 `≥` 或 `:`） | `honor>=100` |

前端会当场检查格式，以及货币 ID 是否是已定义的资源；服务端 `/api/v1/games/validate` 再做一次（未知货币是**错误**）。

### 7.3 引擎怎么算

- **能不能买**：每个价格货币余额 ≥ 价格，且每条门槛满足。
- **还要等多久**：对每个价格货币、每条门槛分别算“攒到需要的数要几秒”，取**最大值**；有任何一项货币产量 ≤ 0 → 视为永远买不到（跳过，不会空转）。
- **性价比**（内置策略和贪心优化器）：卡得最久的那种货币叫“瓶颈货币”。价格按“瓶颈货币数量 × 主货币产量 / 瓶颈货币产量”折成主货币；生产非主货币的生产者，其产出按同样比例折算价值（只有还用得到的货币才算价值）。只用一种货币的物品，结果与旧版完全相同。
- **每段记账**：每个时间段（Segment）记录各货币的 `stock_start`/`stock_end`（期初/期末余额）、`inflow`（产出）、`outflow`（持续消耗）、`spent`（段末购买花掉的）。

### 7.4 静态检查（不模拟，`validate` / CLI `validate` / 全量分析都会跑）

| kind | 含义 |
|---|---|
| `unaffordable` | 某个价格高于该货币上限，永远买不到 |
| `requirement_above_capacity` | 门槛高于该货币上限 |
| `max_owned` | 生产者买到第 N 个之后价格超过上限 |
| `no_source` | 需要的货币没有任何产出来源，初始值不够付 |
| `unreachable_source` | 有来源，但来源本身永远买不到/启动不了 |
| `…+drain` | 同上，且还有持续消耗（净流入恒为负） |
| `unlock_cycle` | 解锁依赖成环 |
| `currency_deadlock` | 货币互相依赖成环（A 的来源要 B，B 的来源要 A），且都没有初始值 → 死锁 |
| `currency_cycle` | 同样成环，但有初始值/外部来源可启动（提示） |

示例游戏：`samples/多货币商店示例/`（金币商店、高级商店、荣誉商店、专属传说券）。

## 8. 与余额挂钩的产出（fix2）

`synergy` 的公式里出现 `balance_<资源ID>` 时，产量会随余额变化。引擎现在在每一段里**精确求解**：
- 公式对余额是线性时（如 `0.01*balance_gold/1000`），用闭式解 `x(t) = x0·e^{kt} + a·(e^{kt}−1)/k`；
- 非线性时（如 `0.1*log10(1+balance_gold)`），用高精度常微分方程积分（相对误差 1e-10）。
生产者/升级的性价比也会把协同加成算进去。注意：`lifetime_*` 变量和 drain 的 `condition` 在一段内仍视为不变。
